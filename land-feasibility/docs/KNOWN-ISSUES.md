## 1. 審查誤判，刻意不改

### 1.1 `m5.legalWarning` 的引號型別（審查員 3，原列輕微）

**指控**：`m5.legalWarning` 用了『』，SPEC 第 7 節的字串是「」，逐字不符。

**查證結果：指控不成立。** SPEC.md 第 330 行原文是：

> `legalWarning` 固定為：「本項為初步判斷，不具法律效力，須由開業建築師簽證。本系統賣的是『值不值得找建築師』，不是『不用找建築師』。」

外層的「」是 SPEC 自己引用整個字串用的引號，**內層的『』才是字串內容**。
`js/engine/m5.js` 的實作與 SPEC 的字串內容逐字相同。改成「」反而會與 SPEC 不符。

**影響**：無。
**建議**：不處理。若日後有人再提同一項，請先讀 SPEC.md 第 330 行本身而不是引用它的段落。

---

### 1.2 抽屜用了 `app.css` 裡不存在的 class（審查員 3，原列輕微）

**指控**：`drawer-ov`、`drawer-review`、`drawer-review-note` 三個 class 在 `assets/app.css` 裡沒有規則，
所以覆寫輸入與「已複核」勾選那一區完全沒有樣式。

**查證結果：前半成立（class 真的沒有規則），後半不成立（版面並沒有沒有樣式）。**
這三個 class 從來不是樣式掛勾，而是 `drawerState()` 的 `querySelector` 用的功能選擇器；
版面是由外層的 `.field`（app.css 有 4 條規則）與 `.checkline`（2 條規則）負責的。

**已做的處理**：把 `drawerState()` 改用 `[data-act="ovInput"]` / `[data-act="reviewToggle"]` /
`[data-act="reviewNote"]` 當選擇器，並把三個 class 從 HTML 中移除。
現在專案裡沒有任何「沒有樣式的 class」，也不會再有人誤以為那三個名字對應到樣式。

**殘留**：`index.html` 的 `main` 與 `unit-switch` 在 `app.css` 裡確實沒有規則。
兩個檔案都在「不准改」清單裡（SPEC 第 2 節、任務鐵則第 7 條），所以沒有動。

**影響**：外觀細節，不影響任何數字。
**建議**：下一次可以改 `index.html` / `app.css` 時一併補上，或確認 `main` 是刻意靠 `body` 的
grid 定位、`unit-switch` 是刻意靠 `.inline` 排版。

## 2. 真實問題，但這一輪沒修

### 2.1 `TD.store.set()` 的路徑檢查沒有涵蓋動態容器內部（部分修復）

**狀態**：主要問題已修。`set()` 現在會用 `pathKnown()` 比對 `defaults()` 的結構，
打錯字的路徑（例如 `m6.presalePremiumX`）一律拒絕寫入並在 `p.audit` 留一筆 `warn`。
實測 UI 上全部 74 個 `data-bind` 路徑都通過檢查，零誤擋（`tools/smoke.js` 之外另有驗收腳本確認）。

**殘留**：`DYNAMIC_PATHS` 白名單（`overrides`、`reviews`、`audit`、`m2.manualFlags`、
`m3.manualChecks`、`m4.pctOverrides`、`m4.picked`、`parcel.numbers`、`m6.comps`）
底下完全不檢查。也就是說 `m4.pctOverrides.GREEEN`（打錯的獎勵 id）仍然會被寫進去，
而 m4 找不到那個 id 就靜默忽略它 —— 使用者以為改了成數，其實沒有。

**會不會搬動出價上限**：不會搬動，但會讓使用者以為自己改了獎勵成數而實際沒改，
進而以錯誤的成數認知去談合建條件。

**建議**：下一輪把動態容器再細分一層 —— `m4.pctOverrides.<id>` 的 `<id>` 要比對
`TD.data.bonus.bonuses` 的 id 清單，`m2.manualFlags.<id>` 比對 m2 的旗標 id 清單。
需要 `pathKnown()` 支援「動態容器 ＋ 合法鍵清單」，不是大工程，但要動到 store 與 data 的耦合。

---

### 2.2 `importJSON` 的結構驗證只擋最粗的情形（部分修復）

**狀態**：`{"foo":1}` 這類完全不像專案檔的物件已經會被擋掉（`ok:false`，並在 warnings 說明原因）；
缺 `parcel` 但有其他模組節點的，會匯入並在 warnings 標明「必須重新輸入基地資料」。

**殘留**：欄位型別沒有逐項驗證。`{"parcel":{"numbers":"不是陣列"}}` 仍會被 `adopt()` 收下，
`adopt()` 會把它換成預設值，但 warnings 不會逐欄說明換了什麼。
使用者匯入一份手改壞的 JSON 時，只會看到一則籠統的警告。

**會不會搬動出價上限**：會 —— 被靜默換成預設值的欄位就是被靜默換掉的假設。
但前提是使用者手改 JSON，不是正常操作路徑。

**建議**：下一輪讓 `adopt()` 對每個被換掉的欄位都 push 一則 warning（目前只有部分欄位有），
並在匯入完成的對話框把 warnings 全部列出來、要求使用者逐條確認。

### 2.3 `m4` 的成本基礎與收入基礎用兩個不同的坪數（設計上的妥協）

**狀態**：收入面已修。`m4.options[].gainPing`（增加可售坪）現在乘上 `(1 + p.m5.exemptRatio)`，
與 `m5.sellablePing` 的算法一致 —— 示範案實測 `gainPing` 193.309 坪，
恰等於「有選獎勵」與「不選獎勵」兩次 `m5.sellablePing` 的差額，兩個模組不再打架。
修正前低估約 36%，而且時程成本沒有同步縮放，偏誤在各制度間不等量
（UR `baseMonths` 36 對 HR 18），跨制度排序有被壓低的風險。

**殘留**：取得成本仍以 `gainPingForCost`（不含免計容積）計價。
理由是 `TD.data.bonus` 的 `costPerGainedPing` 與 `costRateOfPrice` 兩個欄位的註記
明寫單位是「元／每增加一坪可售」，而容積移轉的購入代價實務上是按**移入的容積**算的，
不是按陽台雨遮算的 —— 把成本也乘 1.3 會系統性高估 TDR 與公益設施捐贈的代價。
結果是 `netGain` 的收入面與成本面用兩個不同的坪數，兩者都輸出在 `options` 裡，
並在 `m4.notes` 寫明，但這仍然是一個「同一個公式裡兩種坪」的設計，容易讓複核者看錯。

**會不會搬動出價上限**：不會（出價上限吃的是 `p.m4.picked` 對應的成數，不是排序），
但會搬動「該選哪一組獎勵」的建議，而那個建議會被拿去談合建。

**建議**：下一輪把資料契約寫清楚 —— 在 `js/data/bonus.js` 的 `_meta` 加一個
`costBasis: 'volumePing' | 'sellablePing'` 欄位，逐項標明每一種獎勵的取得成本
到底以容積坪還是可售坪計價，然後 m4 依欄位分別計算。這需要查證各獎勵的實際計價慣例，
屬於「髒活」（原則二），不能靠推論。

### 2.4 `m5` 的層數仍是平均攤算

**狀態**：`floorsAbove` 已改用**總樓地板**（含免計容積）除建築面積，示範案由 10 層修正為 13 層、
高度由 32 m 修正為 41.6 m；另輸出 `volFloors`（容積層數）供對照，UI 上兩個並列並註明用途。
這一項會影響使用者挑營建單價級距（rc12／rc25／src25up）與 m3 的高度比、日照人工複核。

**殘留**：仍然假設「每層都達滿建蔽」。實務上一樓退縮、做店面或車道出入口，
屋突、機電設備層與夾層也沒有扣除，所以真實層數通常還會再高一些。
`m5.notes` 已逐條寫明，但系統不會自己算出來。

**會不會搬動出價上限**：間接會 —— 層數跨過 12 層或 25 層的級距邊界時，
營建單價會跳一級。示範案由 rc25 改 rc12 會讓出價上限位移約 3,500 萬。
但級距是使用者自己選的（`p.m7.constructionKey`），系統不自動切換，這是刻意的。

**建議**：下一輪在 m7 加一則檢查 —— `floorsAbove` 與 `constructionKey` 的級距不相符時
（例如 13 層卻選 rc12），在 m7 的 notes 與 UI 上出現警示，但**不自動改**
（自動改會讓使用者失去對假設的控制感，反而更危險）。

### 2.5 出價上限落在搜尋上界時，`landCap` 本身仍回上界

**狀態**：連帶問題已修。`capOf()` 現在回傳 `clamped` 標記；被夾住時
`sensitivity`／`breakeven`／`scenarios` 的對應欄位一律回 `null` 並在 note 寫明
「解超出搜尋上界，敏感度不可用」，不再出現「五項全部 swing = 0、看起來什麼都不敏感」的龍捲風圖。
`ctx.m8.capClamped` 也輸出出來供 UI 判斷。

**殘留**：`m8.landCap` 本身在被夾住時仍然回上界（總銷 × 0.8）而不是 `null`，
只在 `notes` 說明它不是真正的解。理由是 SPEC 第 7 節寫的是
「`f(上界)` 仍高於目標 → 解超出搜尋範圍，以上界表示並標註」，回 `null` 會與契約不符。

**會不會搬動出價上限**：會 —— 這種情形下畫面上那個「出價上限」根本不是解。
但要進到這個分支，必須讓總銷或成本填到極不合理的值（實測要把營建單價壓到 1,000 元／坪
才觸發），正常輸入不會遇到。

**建議**：跟 SPEC 的作者確認 —— 若同意改，就讓 `landCap` 在 `clamped` 時回 `null`
並把「上界」放在另一個欄位（例如 `landCapClampedAt`）。這是契約層的決定，不該由實作單方面改。

### 2.6 `ctx.m4Rough` 的 V 是重新包裝出來的副本

**狀態**：key 撞號已修。`pipeline.js` 新增 `rekeyV()`，把粗估結果的 key 改前綴為
`m4rough.*`，`TD.collectValues(ctx)` 的 key 現在全部唯一（`tools/smoke.js` 第 14 項守住這件事）。
修正前 `m4.pct`／`m4.bonusFloorM2`／`m4.totalFloorM2` 各出現兩次，
`p.overrides['m4.pct']` 會同時改寫兩處、勾一次「已複核」等於複核兩個數，
而閘門計數靠去重才剛好對得上。

**殘留**：`ctx.m4Rough` 現在是一份**深層複本**，不再與 `ctx.m4` 或 `first` 共用物件。
兩個後果：(a) 記憶體多一份（很小，可忽略）；(b) `p.overrides['m4rough.pct']`
是一個「可以填但沒有意義」的 key —— 覆寫粗估值不會改變任何結果，因為粗估只是中間過程。
UI 上不會出現它的錨點（抽屜找不到就顯示「找不到這個 key」），所以實務上碰不到。

**會不會搬動出價上限**：不會。
**建議**：低優先。若要更乾淨，可以讓 m4 接受 `opts.keyPrefix`，粗估那一輪直接發
`m4rough.*` 的 key，就不需要事後重新包裝。

### 2.7 引擎的 note 不再帶 Markdown，但強調語氣一併消失

**狀態**：已修。`js/engine`、`js/data`、`js/lib` 的**字串常值**內共 91 組 `**` 全部移除
（註解裡的 `**` 保留，不會被渲染）。渲染後的三個版本 × 全部檢視 × 全部 16 張投影片，
字面星號數為 0（修正前：report 82 處、edA 14、m4 6、edB 4、overview 2，
投影片 A#1 2 處、A#2 6 處、B#3 6 處）。

**殘留**：那些句子原本是要**強調**的（「未扣除土地增值稅」「實務上的分回比例是談出來的」
「最終成數由主管機關審議決定」），現在只是普通句子。
審查員 3 的觀察是對的：這些恰好是最需要醒目的避責警語。

**會不會搬動出價上限**：不會，但會降低警語被讀到的機率。

**建議**：下一輪在 UI 層加一個極小的轉換器（`**` → `<strong>`，且**必須發生在 `esc()` 之後**、
只認 `**`），然後把引擎的強調標記加回去。SPEC 沒有禁止這件事，但兩邊都做會出現
字面星號，所以要一次改完：先做 UI 轉換器並驗證，再加回引擎的標記。
目前刻意只做一邊（移除），因為那是唯一能保證「畫面上絕不出現壞掉的文字」的做法。

### 2.8 A 版報告的受眾過濾以章節為單位，不是逐句

**狀態**：主要洩漏已修。`report.js` 新增 `edModules()`／`hasMod()`／`keyAllowed()`，
章節依 `TD.data.editions[id].modules` 過濾（A 版不再輸出 `bonusCard`／`costCard`／
`financeCard`／`sensCard`），數值索引依 `keyAllowed()` 濾掉 `m4.*`／`m7.*`／`m8.*`／
`ed.B.*`／`ed.C.*`，未複核清單保留全部列（SPEC 第 8.4 節要求）但把屬於其他版本的
note 換成中性說明，避免從 note 裡漏出金額。
實測 A 版報告已不含「退場價」「建議貸放成數」「土地融資可貸上限」「擔保價值」
「承接後年化 IRR」「峰值自有資金需求約」。A/B/C 報告長度由 73117/85053/95004
變成 56441/80409/96168。

**殘留**：`ed.A.*` 自己的 `formula` 字串仍然會提到出價上限
（例如 `ed.A.sell.proceeds` 的算式是「賣地價金 = 出價上限 12.92 億元 × 議價折 0.92」）。
這是 A 版本來就該讓地主看到的推導（A 版的整個賣點就是「你這塊地值多少」，
`valueLo`／`valueHi` 本身也是 m8 求解的結果），所以沒有遮蔽。
但嚴格說，一個看得懂算式的仲介可以從這裡反推出建商的出價上限。

**會不會搬動出價上限**：不會搬動數字，但會影響談判資訊對稱性 —— 而那正是 A 版的產品目的
（SPEC 第 5.6 節：A 版的 `judgement` 是「道德上站得住，資訊不對稱極大」）。

**建議**：這是產品決策不是 bug，請產品端拍板：A 版要不要把「出價上限」這個詞
從算式裡換成「本報告的土地價值上緣」。若要換，改 `js/engine/edition.js` 的
`ed.A.*` 算式字串即可，不動計算。

### 2.9 B 版與 C 版報告之間沒有受眾隔離

**狀態**：未修，也不打算在這一輪修。

**說明**：`TD.data.editions.B.modules` 與 `C.modules` 幾乎相同（B 版少了 `m4`、`edC`，
C 版是全部），所以受眾過濾對 B/C 之間幾乎不起作用 —— B 版銀行報告仍然看得到

不在 B 版（銀行是中立方）。

**會不會搬動出價上限**：不會。
**建議**：不處理。除非產品端決定要出一個「只給估價師、不含建商報酬假設」的 B- 版。

### 2.10 `m2` 只有兩個 `high` 信心的數字

**狀態**：已修最關鍵的部分。`m2.consent` 新增四個 V：
`m2.consentThresholdHalf`（0.5，conf `high`）、`m2.consentThresholdTwoThirds`（2/3，conf `high`）、

既有的 `consent.ownerRatio`／`shareRatio`／`pass` 等裸欄位**型別完全沒動**，
因為 `js/data/editions.js` 與 `js/ui/views-site.js` 都在讀它們。

**殘留**：其他真正屬於法規明文的數字仍然標 `unv`，例如
`TD.data.bonus` 的 `capOfBase`（都更 50%、危老 30%）與 `_meta.tdrCapOfBase`（30%）。
這些**應該**是 `high`（都更條例第65條、危老條例第6條都是明文），
但按 SPEC 第 3 節「所有 `js/data/*.js` 內的法規數值預設都是 `unv`」的規定，
在逐字核對之前一律標 `unv`。

**會不會搬動出價上限**：不會。但會稀釋徽章的訊號價值 ——
如果九成的數字都是「待查」，使用者很快就會停止看徽章。

**建議**：這是 `docs/DATA-VERIFICATION.md` 的工作，不是程式的工作。
每查證一項就把該項的 `verified` 改 `true`，引擎自然會把它升級成 `high`。
建議先查最會搬動數字的三項：都更與危老的 `capOfBase`、臺北市商三的 `far`、
臺北市的停車換算標準 `residentialPerM2`。
